## 本次更新内容摘要

### 缺陷：新增 GLaDOS 账号会覆盖已有账号
- 现象：已有若干 GLaDOS 账号后，再点「添加账号」录入新账号并保存，新账号没有被创建，而是把之前某个已有账号的名称与 Cookie 整条替换掉。
- 排查：
  - 后端 `createAccount` 是纯 `INSERT`，`glados_checkin_accounts` 上没有唯一约束，也没有 upsert 语义，后端无问题。
  - 线上库确认 3 个 GLaDOS 账号（id 2/3/4）均存在，未丢账号；其中 id=4 的 `updated_at` 比 `created_at` 晚 278 秒，且 id=2/3 的 `updated_at` 相差 1 秒（属批量签到写入），说明只有 id=4 发生过一次「本应新增却变成更新」的手工写入。
- 根因：前端 `editingGladosAccount` 这个 ref 只在 `openEditGladosModal` 中被赋值，**没有任何路径把它复位为 `null`**。而 `submitGladosAccount` 正是依据该 ref 判断走新增还是更新分支。因此只要点过一次 GLaDOS 的「编辑」，此后每次「添加账号」都会静默走 `PUT` 更新，把那个账号覆盖掉。
- 同类根源：弹框复位逻辑此前被复制成三份（`openCreateModal` / `openPokemonModal` / `resetAccountModalContext`），新增 `editingGladosAccount` 时只有其中的赋值点被更新，复位点全部漏掉。公益站的 `editingAccount` 在三处都有复位，所以未受影响。
- 修复：
  - `resetAccountModalContext` 增加 `editingGladosAccount.value = null`。
  - 将 `resetAccountModalContext` 收敛为弹框的唯一复位入口，`openCreateModal` / `openPokemonModal` / `openEditModal` / `openEditGladosModal` 四个打开路径一律先调用它，再设置各自差异项，消除复制粘贴导致复位项漏更新的结构性隐患。

## 本次验证范围
- `npm run typecheck` 通过；全量测试 100 项通过；`npm run build` 通过。
- 本仓库无前端组件测试设施（`tests/` 全部为 `node:test` 的服务端用例），该缺陷属于 Vue 组件状态问题，为此单独引入 vitest 不在本次修复范围内，改以 Playwright 对本地生产构建做真实回归。
- 回归脚本按用户实际操作路径驱动真实 UI：新增 acc-1/acc-2/acc-3 → 对 acc-3 点「编辑」后取消 → 再次「添加账号」录入 acc-4。
  - **修复前**：`[5:acc-1, 6:acc-2, 7:acc-3]` → `[5:acc-1, 6:acc-2, 7:acc-4]`，acc-3 被顶替，acc-4 未创建 —— 与用户反馈现象一致，确认脚本能复现。
  - **修复后**：`[8:acc-1, 9:acc-2, 10:acc-3, 11:acc-4]`，四个账号并存。
- 公益站路径回归：先编辑一个 GLaDOS 账号并取消制造状态污染，再新增 site-A/site-B、编辑 site-A 改名，结果为 `[2:site-A-renamed, 3:site-B]`，新增走新增、编辑走编辑，未受影响。
